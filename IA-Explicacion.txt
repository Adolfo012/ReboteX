Explicación de la IA (Árbol de Decisión) - ReboteX
Fecha: actual

Objetivo
- Predecir el equipo favorito de un partido de torneo usando un modelo de árbol de decisión entrenado con estadísticas agregadas de los equipos en ese torneo. Cuando no hay modelo (o hay pocos datos), se aplica una heurística estable y ajustes conservadores.

Arquitectura General
- ml/train.py: construye el conjunto de datos desde la base de datos y entrena el árbol de decisión (DecisionTree) con calibración de probabilidades. Guarda el modelo en ml/models/favorite_dt.pkl.
- ml/service.py: servicio HTTP (FastAPI) que carga el modelo entrenado, arma el vector de características de ambos equipos y devuelve favorito y probabilidad. Si el modelo no existe, usa la heurística.
- backend/routes/partidos.js: endpoint GET /api/partidos/:id/favorito que calcula agregados por equipo, consulta al servicio ML y post-procesa la probabilidad con los mismos ajustes para pocos datos. Si el servicio ML no responde, aplica la heurística local. También construye una explicación narrativa para el tooltip del frontend.

Datos y Features (por equipo, dentro del torneo)
- pj: partidos jugados (solo con resultados, se ignoran 0-0 o vacíos).
- pg: partidos ganados; pp: perdidos.
- pf: puntos a favor totales; pc: puntos en contra totales; diff = pf - pc.
- pt: puntos por triples; pd: puntos por dobles; tl: tiros libres.
- pa: puntos totales del equipo en el torneo (pt*3 + pd*2 + tl).
- Derivados por partido: pf_pg = pf/pj; pc_pg = pc/pj; diff_pg = (pf - pc)/pj.
- win_rate: tasa de victoria con suavizado de Laplace para evitar extremos al inicio ((pg+1)/(pj+2) si pj>0; 0.5 si pj=0).

Entrenamiento del Modelo (ml/train.py)
- Selección de partidos: usa solo partidos con resultados y descarta empates.
- Construction del dataset: para cada partido, se calculan las features del local (A) y visitante (B) y la etiqueta label=1 si gana el local, 0 si gana el visitante.
- Vector de entrenamiento (16 features + 1 etiqueta):
  - A: win_rate, pf_pg, pc_pg, diff_pg, pa, pt, pd, tl.
  - B: win_rate, pf_pg, pc_pg, diff_pg, pa, pt, pd, tl.
- Árbol de decisión (DecisionTreeClassifier) con hiperparámetros adaptados al tamaño del conjunto:
  - ≤24 muestras: max_depth=2, min_samples_leaf=5, min_samples_split=6, class_weight='balanced'.
  - ≤60 muestras: max_depth=3, min_samples_leaf=6, min_samples_split=10, class_weight='balanced'.
  - ≤150 muestras: max_depth=5, min_samples_leaf=5, class_weight='balanced'.
  - >150 muestras: max_depth=8.
- Calibración de probabilidades (CalibratedClassifierCV, método 'sigmoid') para mayor estabilidad:
  - Si el set de entrenamiento es muy pequeño (min_class<4 o <40 ejemplos), se usa cv='prefit'.
  - Si hay más datos, cv=3 para calibración out-of-fold.
- Métricas reportadas: accuracy y Brier score (si aplica). El modelo calibrado se guarda en ml/models/favorite_dt.pkl.
- Si hay <8 partidos totales, se omite entrenamiento y el servicio usa heurística.

Servicio de Predicción (ml/service.py)
- Carga el modelo desde ml/models/favorite_dt.pkl. Si no existe o falla, se usa heurística.
- Construcción de features en predicción:
  - _compose_pair_features(a,b) concatena las 8 features de A y 8 de B.
  - win_rate se recalcula con Laplace si no viene en el payload.
- Predicción con modelo:
  - predict_proba → probabilidad de victoria de A. Se define el favorito por prob≥0.5.
  - prob_raw se normaliza para siempre representar la probabilidad del favorito (si fue B, se usa 1-prob_A).
- Heurística fallback (cuando no hay modelo):
  - score(x) = 0.5*win_rate + 0.3*diff_pg + 0.15*pf_pg + 0.05*pa_scaled, con pa_scaled = log(1 + pa_por_partido)/8.
  - prob_A = 1 / (1 + exp(-(score_A - score_B))). Se normaliza del lado del favorito.
- Ajustes para pocos datos (aplicados tanto a modelo como a heurística):
  - Shrink hacia 0.5 según min(pj) entre ambos equipos:
    - min(pj)=1→0.25, 2→0.35, 3→0.50, 4→0.60, 5→0.70, 6→0.80, 7–8→0.90, 9–10→0.95, ≥11→1.00 (factor que reduce desviación respecto a 0.5).
  - Cap dinámico simétrico: limita confianza máxima/minima alrededor de 0.5:
    - 55% (pj≤1), 60% (2), 65% (3), 70% (4), 75% (5), 80% (≤7), 85% (≤9), 90% (≥10).
  - Paridad: si win_rate, diff_pg y pf_pg son muy similares (umbrales: 0.08, 2.0 y 2.0), se reduce otro 30% de la desviación.

Integración con el Backend (backend/routes/partidos.js)
- Endpoint GET /api/partidos/:id/favorito:
  - Calcula agregados A y B desde la DB (mismas métricas que en entrenamiento).
  - Calcula racha de victorias (getStreakWins) para enriquecer la explicación.
  - Consulta al servicio ML (ML_SERVICE_URL; por defecto http://localhost:8001).
  - Reaplica los mismos ajustes pequeños (shrink + cap) para consistencia.
  - Si el ML no responde, aplica la misma heurística local.
  - Devuelve explain con métricas y una narrativa en lenguaje natural (explain.summary), que compara diferenciales, promedios y tasa de victoria, y añade racha y promedios de los “jugadores estrella”.
- Jugadores estrella: se calcula el máximo anotador por equipo en el torneo y su promedio de puntos por partido (COUNT DISTINCT de partido_id sobre partido_jugadores).

Qué NO usa actualmente el modelo
- Enfrentamientos directos específicos entre los dos equipos del partido (head-to-head del par actual).
- Secuencias temporales o recencia explícita; todo es histórico agregado del torneo.
- Señal de localía independiente (el vector A es el local, pero no se añade un flag “es local”).

Comportamiento con pocos datos
- El modelo y la heurística se mantienen conservadores al inicio del torneo gracias al shrink y al cap dinámico.
- En situaciones de paridad de métricas, se evita sobreconfianza reduciendo la desviación adicionalmente.

Endpoints y rutas
- Servicio ML: POST /predict_favorite (FastAPI, ml/service.py).
- Backend: GET /api/partidos/:id/favorito (Express, backend/routes/partidos.js).

Reentrenamiento (referencia rápida)
- Configurar variables de entorno de la DB (DATABASE_URL o DB_HOST/DB_NAME/DB_USER/DB_PASSWORD).
- Ejecutar el script de entrenamiento (entorno Python con requisitos de ml/requirements.txt).
- Si el entrenamiento genera ml/models/favorite_dt.pkl, el servicio ML lo usará automáticamente.

Resumen
- El árbol de decisión aprende a partir de señales agregadas por partido (win_rate, diff_pg, pf_pg, pa, etc.).
- La predicción final se estabiliza con calibración y ajustes de pequeños tamaños de muestra.
- El backend añade una explicación narrativa y datos de racha y máximos anotadores para que el usuario entienda por qué un equipo es favorito.
